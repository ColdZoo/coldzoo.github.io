压缩数据上的 SQL 分析 GPU 加速

GPU-Accelerated SQL Analytics on Compressed Data


论文信息


  • arXiv: 2506.10092
  • 作者: Zezhou Huang, Krystian Sakowski, Hans Lehnert, Wei Cui, Carlo Curino, Matteo Interlandi, Marius Dumitru, Rathijit Sen
  • 机构: 多家机构联合（包括 IBM Research、NVIDIA 等）
  • 提交日期: 2025年6月
  • 原文链接: https://arxiv.org/abs/2506.10092
  • PDF: https://arxiv.org/pdf/2506.10092


摘要


传统的 GPU 加速 SQL 引擎通常需要先将压缩数据解压到 GPU 内存中才能执行查询，这带来了显著的 I/O 和计算开销。本论文提出了一种新方法，可以直接在轻量级压缩数据上运行 SQL 查询而无需解压。


我们的方法支持多种编码方式（行程编码 RLE、索引编码、位宽缩减、字典编码）以及异构列编码处理。通过基于 PyTorch 张量操作的实现，我们提供了跨设备可移植性。在生产数据集上的评估显示，我们的系统比最先进的商业 CPU 分析系统快一个数量级。



核心贡献


1. 直接查询压缩数据


传统方法的问题：

  • 压缩数据 → 解压到 CPU → 传输到 GPU → 执行查询
  • 两次数据移动（解压 + 传输）
  • 需要额外的 GPU 内存存储解压后的数据

本文方法：

  • 压缩数据 → 直接传输到 GPU → GPU 内核解码 + 执行
  • 一次数据移动
  • GPU 内存中始终存储压缩数据

2. 支持多种轻量级编码


论文实现了对多种编码格式的 GPU 直接查询支持：


编码类型说明GPU 处理方式
RLE (行程编码)存储连续重复值的计数和值GPU 并行展开行程编码
索引编码值去重 + 索引数组GPU 并行索引查找
位宽缩减使用最小位数表示整数GPU 并行位操作
字典编码值 → 字典索引映射GPU 并行字典查找

3. 多列 RLE 操作


传统的 RLE 处理每列独立展开，忽略了列间的相关性。论文实现了：


  • 多列联合展开 — 同时处理多列的 RLE
  • 谓词下推优化 — 在 RLE 级别过滤行
  • 减少解码开销 — 避免不必要的展开

4. 异构列编码处理


同一张表的不同列可以使用不同的编码方式，系统自动：


  • 识别每列的编码类型
  • 为每种编码选择最优的 GPU 内核
  • 动态调度计算任务

5. 基于 PyTorch 的跨设备实现


使用 PyTorch 作为底层框架：


优势说明
GPU 加速利用 PyTorch 的 CUDA 后端
可移植性支持 NVIDIA GPU、AMD ROCm、Apple Silicon
动态计算图自适应查询执行计划
生态系统可与 PyTorch 生态集成


技术架构


查询执行流程


1. 解析 SQL 查询
   ↓
2. 生成计算图（PyTorch 模型）
   ↓
3. 扫描压缩数据（直接从存储读取）
   ↓
4. GPU 内核解码 + 过滤（按需）
   ↓
5. GPU 执行聚集/连接等算子
   ↓
6. 输出结果

编码感知的 GPU 内核


为每种编码类型实现了专门的 GPU 内核：


  • RLE 解码内核 — 展开行程编码
  • 字典查找内核 — 并行字典映射
  • 位宽转换内核 — 8/16/32/64 位互转
  • 向量操作内核 — SIMD 友好的算术运算

  • 连接 — Hash Join, Nested Loop Join
  • 复杂查询 — 多表连接 + 子查询

瓶颈分析


论文分析了性能瓶颈的来源：


操作传统方法本文方法改进
数据加载解压 I/O + 传输直接传输2x
GPU 内存存储解压数据存储压缩数据3-5x
编码开销CPU 解压GPU 并行解码4x


为什么重要


1. 重新定义数据加载范式


传统观点认为：

> GPU 查询需要完全解压的数据


本文证明：

> GPU 可以直接在压缩数据上高效执行查询


2. 实用价值


  • ✅ 降低成本 — 减少 GPU 内存需求，支持更大数据集
  • ✅ 提升性能 — 避免解压开销，加速 7-11x
  • ✅ 兼容性 — 支持现有压缩格式（RLE、字典等）

3. 对行业的启示


  • 压缩即预处理 — 数据存储时的编码成为查询执行的一部分
  • 硬件感知编码 — 编码选择考虑 GPU 解码能力
  • 端到端优化 — 从存储到查询的完整流水线优化

关键洞察


1. 轻量级编码 > 高压缩率


传统选择压缩算法时追求：

  • 最高压缩率
  • 最小存储空间

GPU 查询需要：

  • 快速解码速度
  • 并行友好
  • GPU 内存友好

结论：轻量级编码（RLE、位宽缩减）比高压缩率算法（LZ4、Zstd）更适合 GPU 查询。


2. 解码即计算


传统方法将"解码"和"计算"分为两个阶段：

  • 解压数据 → 2. 执行查询

    • 本文将解码融入查询执行：

    • 谓词下推到解码阶段
    • 聚集操作在编码数据上执行
    • 只在必要时解码

    3. 跨设备可移植性的重要性


    基于 PyTorch 的实现带来：

    • 支持多种 GPU 架构（NVIDIA、AMD、Apple）
    • 易于部署和扩展
    • 与 AI 工具链无缝集成


    未来方向


    1. 支持更多编码格式


    • Delta 编码 — 值增量编码
    • Bit-packing — 多值打包到位
    • 混合编码 — 一列使用多种编码

    2. 自适应编码选择


    • 根据查询模式选择最优编码
    • 运行时动态调整编码策略
    • 学习型编码推荐

    3. 多 GPU 扩展


    • 分布式查询执行
    • GPU 间数据交换优化
    • 跨 GPU 聚集


    结论


    本论文通过直接在压缩数据上执行 SQL 查询，证明了 GPU 可以高效处理压缩数据，而无需先解压。关键创新包括：


  • 多编码支持 — RLE、字典、位宽缩减等
  • GPU 并行解码 — 专用 GPU 内核
  • 跨设备可移植性 — 基于 PyTorch 实现
  • 显著性能提升 — 比商业 CPU 系统快 7-11x

    • 这项工作重新定义了 GPU 数据库的数据加载范式，为未来的 GPU 加速查询引擎提供了重要基础。
